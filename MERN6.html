1. Introduction to Mongoose

Core Concept

Mongoose is an ODM (Object Data Modeling) library for MongoDB and Node.js. It sits on top of the official MongoDB driver and adds schemas, validation, type casting, middleware (hooks), population (joins) and a clean query API. It is the standard way to talk to MongoDB in MERN apps.

Why Mongoose when MongoDB is already "schema-flexible"?

  • The raw driver accepts any shape of document, so typos and wrong types silently enter the database.
  • Mongoose gives your data a structure in application code, with defaults, validation and business logic attached to the model.
  • It returns rich document objects (with methods, virtuals, save()) rather than plain objects.
Aspect Native mongodb driver Mongoose
Schema None Defined in code
Validation Only server-side $jsonSchema Built-in and custom, at the app level
Type casting None Automatic ("22" → 22)
Middleware / hooks No Yes (pre / post)
Relationships Manual $lookup populate()
Boilerplate More Less
Speed Slightly faster Slight overhead (reduce with lean())

                        │

                  MongoDB driver ──► MongoDB server (BSON)

 Hierarchy:   Schema  ──compile──►  Model  ──new──►  Document  ──save()──►  MongoDB

Key Concept: Schema = blueprint, Model = constructor/class bound to a collection, Document = an instance of a model.
Exam Trap: Mongoose is an ODM (for document databases), not an ORM (for relational databases like Sequelize). It is not a database; MongoDB must still be running. Mongoose schemas are enforced in the application, not in the database, so another client can still write invalid data.

3. Connecting to MongoDB from Mongoose

Core Concept

mongoose.connect(uri, options) opens a connection (pool) to MongoDB and returns a Promise. The URI contains host, port, database name and options.

Connection strings

Type Example
Local mongodb://127.0.0.1:27017/shopDB
With auth mongodb://user:pass@127.0.0.1:27017/shopDB?authSource=admin
Atlas mongodb+srv://user:pass@cluster0.abcde.mongodb.net/shopDB?retryWrites=true&w=majority
Replica set mongodb://h1:27017,h2:27017/shopDB?replicaSet=rs0 
// config/db.js
const mongoose = require("mongoose");

const connectDB = async () => {
  try {
    const conn = await mongoose.connect(process.env.MONGO_URI, {
      serverSelectionTimeoutMS: 5000,   // fail fast if server unreachable
      maxPoolSize: 10                   // connections in the pool
      // dbName: "shopDB"               // alternative to putting db in the URI
    });
    console.log(`MongoDB connected: ${conn.connection.host}/${conn.connection.name}`);
  } catch (err) {
    console.error("MongoDB connection failed:", err.message);
    process.exit(1);                    // no DB, no app
  }
};

4. Core Concepts of Mongoose

Everything in Mongoose revolves around six building blocks:

Concept Meaning Example
Schema Defines fields, types, validation, defaults, indexes new Schema({ name: String })
Model Compiled schema; gives the CRUD API for a collection mongoose.model("User", schema)
Document One instance of a model; has save(), validate() new User({...})
Query Chainable, lazy object returned by find() etc. User.find().sort().limit()
Middleware (hooks) Functions run before/after events (save, find...) schema.pre("save", fn)
Populate Replace stored ObjectId references with real documents Post.find().populate("author") 
const mongoose = require("mongoose");
const { Schema } = mongoose;

// 1. Schema
const userSchema = new Schema({ name: String, email: String, age: Number });

// 2. Model  → collection name = lower-case plural of the model name: "users"
const User = mongoose.model("User", userSchema);

// 3. Document
const u = new User({ name: "Asha", email: "a@x.com", age: "22" });   // "22" cast to 22
await u.save();                                // INSERT

// 4. Query (lazy until awaited / .exec())
const q = User.find({ age: { $gt: 18 } }).sort({ age: -1 }).limit(5);
const users = await q;                         // executes now

// 5. Middleware
userSchema.pre("save", function (next) { console.log("saving", this.name); next(); });

// 6. Populate
const postSchema = new Schema({ title: String, author: { type: Schema.Types.ObjectId, ref: "User" } });
const Post = mongoose.model("Post", postSchema);
const posts = await Post.find().populate("author", "name email");   // author becomes a user object

Casting and validation flow

 new User(data) ──► CAST types per schema ──► apply defaults/setters
                                          │
 doc.save() ──► pre("validate") ──► VALIDATE ──► pre("save") ──► insert/update ──► post("save")
                                      │ fail
                                      ▼
                              ValidationError (nothing written)

Instance methods, statics and query helpers

userSchema.methods.greet = function () { return `Hi, ${this.name}`; };           // on documents
userSchema.statics.findByEmail = function (email) { return this.findOne({ email }); }; // on the Model
userSchema.query.adults = function () { return this.where({ age: { $gte: 18 } }); };   // chainable helper

const doc = await User.findByEmail("a@x.com");
doc.greet();
await User.find().adults().sort("name");

Middleware examples

const bcrypt = require("bcrypt");
userSchema.pre("save", async function () {                   // hash password before saving
  if (!this.isModified("password")) return;                  // only when changed
  this.password = await bcrypt.hash(this.password, 10);
});
userSchema.post("save", function (doc) { console.log("saved", doc._id); });
userSchema.pre("find", function () { this.where({ isDeleted: { $ne: true } }); });   // query middleware
Key Concept: A Mongoose Query is thenable (lazy). It runs only when you await it, call .then() or .exec(). Mongoose 8 has no callback support.
Exam Trap: Inside hooks and methods use a normal function, not an arrow function, because you need this. Query/update middleware (findOneAndUpdate) does not run pre("save"); document hooks and query hooks are different. save() hooks run only on doc.save() and Model.create(), not on insertMany in the same way or updateOne. Model name "User" → collection users (override with the collection schema option).

5. Understanding Mongoose Schemas and Datatypes

Core Concept

A Schema maps to a MongoDB collection and defines the shape of its documents: field names, types, defaults and validation rules. It is created with new mongoose.Schema(definition, options).

SchemaTypes (datatypes)

Type Declaration Notes
String String Many string-specific options
Number Number Integer or float; min/max
Date Date JS Date, min/max
Boolean Boolean Casts "true", 1 to true
ObjectId Schema.Types.ObjectId Used with ref for relations
Array [String], [{...}] Array of a type or of subdocuments
Buffer Buffer Binary data
Mixed Schema.Types.Mixed or {} Any type; no casting; must call markModified()
Decimal128 Schema.Types.Decimal128 Exact decimals (money)
Map Map (with of) Dynamic string keys
UUID, BigInt Schema.Types.UUID, BigInt Special ids/numbers
Nested / Subdocument { address: { city: String } } or new Schema({...}) Embedded structure

Schema example using all main features

const mongoose = require("mongoose");
const { Schema } = mongoose;

// Reusable subdocument schema (gets its own _id unless { _id: false })
const addressSchema = new Schema({
  street: String,
  city:   { type: String, required: true },
  pin:    { type: String, match: /^\d{6}$/ }
}, { _id: false });

const studentSchema = new Schema({
  name:      { type: String, required: [true, "Name is required"], trim: true },
  email:     { type: String, required: true, unique: true, lowercase: true },
  age:       { type: Number, min: 16, max: 60 },
  isActive:  { type: Boolean, default: true },
  dob:       Date,
  cgpa:      Schema.Types.Decimal128,
  skills:    [String],                                   // array of strings
  address:   addressSchema,                              // single subdocument
  addresses: [addressSchema],                            // array of subdocuments
  meta:      Schema.Types.Mixed,                         // anything
  scores:    { type: Map, of: Number },                  // { math: 90, sci: 80 }
  course:    { type: Schema.Types.ObjectId, ref: "Course" },  // reference
  profile:   { bio: String, website: String }            // nested object (no separate schema)
}, {
  timestamps: true,        // auto createdAt, updatedAt
  versionKey: "__v",       // set false to remove the version key
  collection: "students",  // explicit collection name
  strict: true,            // ignore fields not in schema (default)
  toJSON: { virtuals: true }
});

const Student = mongoose.model("Student", studentSchema);

Schema options (second argument)

Option Effect
timestamps Adds and maintains createdAt / updatedAt
strict true (default) drops unknown fields; false saves them; "throw" errors
versionKey Name of the __v revision field (or false)
collection Override collection name
_id false removes auto _id (subdocuments)
toJSON / toObject Include virtuals, transform output
minimize Drops empty objects by default
autoIndex Build declared indexes automatically
discriminatorKey Inheritance between models

Casting behaviour

new Student({ age: "25" }).age;          // 25 (number)
new Student({ isActive: "true" }).isActive;  // true
new Student({ age: "abc" }).validateSync();  // CastError: Cast to Number failed for value "abc"
new Student({ nickname: "x" }).nickname;     // undefined (not in schema, strict mode)

// Mixed type: Mongoose cannot detect changes
doc.meta.theme = "dark";
doc.markModified("meta");
await doc.save();
 Schema fields ───► SchemaType ───► Validators / Setters / Defaults
   name: String       String            required, trim, minlength ...
   age : Number       Number            min, max
   tags: [String]     Array(String)
   addr: {city:...}   Subdocument       its own validation
 Stored in MongoDB as BSON:  String→string, Number→double/int, Date→date, ObjectId→objectId
Exam Trap: Passing a type name as a string, an unrecognised type, or forgetting the type key when a field is named type are common bugs. With strict: true extra fields are silently discarded. Mixed fields need markModified(). Arrays default to [] (not undefined). Subdocument schemas get an _id unless disabled. For money use Decimal128 or store integer paise/cents. Number is stored as double, so there is no separate Int schema type by default. { name: String } is shorthand for { name: { type: String } }.

6. Working with Models

Core Concept

A Model is the compiled version of a schema and acts as an interface to one collection. Documents are instances of the model. All CRUD operations go through the model.

Creating a model

// models/User.js
const mongoose = require("mongoose");
const userSchema = new mongoose.Schema({
  name:  { type: String, required: true },
  email: { type: String, required: true, unique: true },
  age:   Number
}, { timestamps: true });

module.exports = mongoose.model("User", userSchema);   // collection: "users"
// Avoid OverwriteModelError in hot reload: mongoose.models.User || mongoose.model("User", userSchema)

CREATE

const User = require("./models/User");

// A. new + save (runs validation and hooks; lets you modify before saving)
const u = new User({ name: "Asha", email: "a@x.com", age: 22 });
await u.save();

// B. create (shortcut for new + save; accepts one or an array)
const u2  = await User.create({ name: "Ravi", email: "r@x.com" });
const many = await User.create([{ name: "A", email: "a1@x.com" }, { name: "B", email: "b1@x.com" }]);

// C. insertMany (one DB call, fast; validates each document)
await User.insertMany([{ name: "C", email: "c@x.com" }], { ordered: false });

READ

await User.find();                                   // all (array)
await User.find({ age: { $gte: 18 } });              // with filter (same operators as MongoDB)
await User.findOne({ email: "a@x.com" });            // first match or null
await User.findById("665f1c2a9b1e8a3d4c5e6f70");     // by _id (string auto-cast); null if absent
await User.countDocuments({ age: 22 });
await User.exists({ email: "a@x.com" });             // { _id } or null

// Chaining
await User.find({ age: { $gt: 18 } })
  .select("name email -_id")        // projection: include name,email; exclude _id
  .sort({ age: -1 })                // or .sort("-age")
  .skip(10).limit(10)               // pagination
  .lean();                          // plain JS objects (faster, no document methods)

// Query builder style
await User.where("age").gt(18).lt(30).select("name");

// Populate
await Post.find().populate({ path: "author", select: "name" });

UPDATE

// A. Find → modify → save (runs full validation and save hooks)
const user = await User.findById(id);
user.age = 23;
await user.save();

// B. Direct update (single atomic DB operation)
await User.updateOne({ email: "a@x.com" }, { $set: { age: 24 } });
await User.updateMany({ age: { $lt: 18 } }, { $set: { minor: true } });

// C. Find and update, returning the document
const updated = await User.findByIdAndUpdate(
  id,
  { name: "New Name" },
  { returnDocument: "after", runValidators: true }   // "new: true" is the older equivalent
);

await User.findOneAndUpdate({ email: "x@x.com" }, { $inc: { age: 1 } }, { upsert: true, returnDocument: "after" });
await User.replaceOne({ _id: id }, { name: "Replaced", email: "r@r.com" });

DELETE

await User.deleteOne({ email: "a@x.com" });          // → { acknowledged, deletedCount }
await User.deleteMany({ age: { $lt: 18 } });
const gone = await User.findByIdAndDelete(id);       // returns deleted document or null
await user.deleteOne();                               // on a document instance
// Model.remove() was REMOVED in Mongoose 7+; use deleteOne / deleteMany

Full Express controller

// controllers/userController.js
const User = require("../models/User");
const mongoose = require("mongoose");

exports.create = async (req, res) => {
  try {
    const user = await User.create(req.body);
    res.status(201).json(user);
  } catch (err) {
    if (err.code === 11000) return res.status(409).json({ error: "Email already exists" });   // duplicate key
    if (err.name === "ValidationError") return res.status(400).json({ error: err.message });
    res.status(500).json({ error: "Server error" });
  }
};

exports.list = async (req, res) => {
  const { page = 1, limit = 10 } = req.query;
  const users = await User.find().sort("-createdAt").skip((page - 1) * limit).limit(+limit).lean();
  res.json(users);
};

exports.getOne = async (req, res) => {
  if (!mongoose.isValidObjectId(req.params.id)) return res.status(400).json({ error: "Invalid id" });
  const user = await User.findById(req.params.id);
  if (!user) return res.status(404).json({ error: "Not found" });
  res.json(user);
};

exports.update = async (req, res) => {
  const user = await User.findByIdAndUpdate(req.params.id, req.body, { returnDocument: "after", runValidators: true });
  user ? res.json(user) : res.status(404).json({ error: "Not found" });
};

exports.remove = async (req, res) => {
  const user = await User.findByIdAndDelete(req.params.id);
  user ? res.sendStatus(204) : res.status(404).json({ error: "Not found" });
};

// routes: router.route("/").get(list).post(create); router.route("/:id").get(getOne).put(update).delete(remove);

Find one / by id findOne / findById findOne({_id})

Key Concept: lean() returns plain objects instead of Mongoose documents, which makes read queries much faster and lighter, but you lose save(), virtuals (unless a plugin is used), getters and methods.
Exam Trap (high-yield):
  • Update validators do NOT run by default on updateOne, findByIdAndUpdate etc.; pass runValidators: true.
  • findByIdAndUpdate returns the old document unless you set returnDocument: "after" (or new: true).
  • findById with a malformed id throws a CastError; findById with a valid but non-existent id returns null, not an error.
  • Always await; forgetting it gives you a Query/Promise object instead of data.
  • find() returns an array (possibly empty), findOne() returns an object or null.
  • Duplicate-key errors have err.code === 11000 (from the unique index).
  • Model name is singular and capitalised (User); the collection is plural and lower-case (users).
  • Mongoose 8 removed callbacks and Model.remove(); in Mongoose 7+ strictQuery is false by default.

7. Using Modifiers in Schema

Core Concept

Schema modifiers are options attached to a field that transform its value (setters, getters, defaults), validate it, or control visibility and indexing. They keep data consistent without writing code in every route.

A. Built-in transformation modifiers (String)

Modifier Effect
trim: true Strip leading/trailing spaces
lowercase: true Convert to lower-case before saving
uppercase: true Convert to upper-case
default: value | fn Value used when the field is undefined
set: fn Custom setter, runs on write
get: fn Custom getter, runs on read
immutable: true Cannot be changed after creation
select: false Excluded from query results by default (e.g., password)
alias: "x" Virtual alias for the field

B. Validation modifiers

Applies to Validators
All types required (can be [true, "message"]), validate (custom)
String minlength, maxlength, match (regex), enum
Number, Date min, max
Array custom validate (e.g., length limits) 
const productSchema = new mongoose.Schema({
  // required with custom message
  name: { type: String, required: [true, "Product name is required"], trim: true,
          minlength: [3, "Min 3 characters"], maxlength: 100 },

  // lowercase + unique + regex
  sku: { type: String, required: true, unique: true, uppercase: true,
         match: [/^[A-Z]{3}-\d{4}$/, "SKU format must be ABC-1234"] },

  // enum
  category: { type: String, enum: { values: ["Electronics", "Books", "Clothing"], message: "{VALUE} is not a valid category" } },

  // number range + default + setter (round to 2 decimals) + getter (format)
  price: { type: Number, required: true, min: [0, "Price cannot be negative"],
           set: v => Math.round(v * 100) / 100,
           get: v => Number(v).toFixed(2) },

  stock: { type: Number, default: 0, min: 0, max: 10000 },

  // default as a function (evaluated on each new document)
  createdOn: { type: Date, default: Date.now },        // pass the function, do NOT call it: Date.now()
  releaseDate: { type: Date, min: "2020-01-01" },

  // custom validator (sync) and async validator
  discount: { type: Number, validate: { validator: v => v <= 90, message: "Discount cannot exceed 90%" } },
  barcode:  { type: String, validate: { validator: async v => !(await mongoose.models.Product.exists({ barcode: v })),
                                          message: "Barcode already used" } },

  // array validation
  tags: { type: [String], validate: [arr => arr.length <= 5, "Max 5 tags"] },

  // immutable
  createdBy: { type: String, immutable: true },

  // hidden by default
  secretNotes: { type: String, select: false },

  // conditional required
  reason: { type: String, required: function () { return this.stock === 0; } }
}, { timestamps: true, toJSON: { getters: true } });

Exam Trap: unique: true is not a validator; it creates a unique index, so violations produce a MongoDB error E11000 (code 11000), not a ValidationError. required fails for undefined/null (and empty string for String). default: Date.now (function) vs default: Date.now() (frozen at server start) is a classic bug. min/max are for Number/Date, minlength/maxlength for String. Getters are not applied in toJSON unless { getters: true }.

8. Using Virtual Fields

Core Concept

A virtual is a property that exists on the Mongoose document but is not stored in MongoDB. It is computed from real fields (getter) and can optionally split input into real fields (setter). Typical uses: fullName, age from dob, formatted values, and reverse relationships. 

const personSchema = new mongoose.Schema({
  firstName: String,
  lastName:  String,
  dob:       Date,
  price:     Number,
  taxRate:   { type: Number, default: 0.18 }
}, {
  toJSON:   { virtuals: true },     // include virtuals in res.json() / JSON.stringify
  toObject: { virtuals: true }      // include virtuals in doc.toObject()
});

// GETTER
personSchema.virtual("fullName").get(function () {
  return `${this.firstName} ${this.lastName}`;
});

// GETTER + SETTER
personSchema.virtual("name")
  .get(function () { return `${this.firstName} ${this.lastName}`; })
  .set(function (value) {
    const [first, ...rest] = value.split(" ");
    this.firstName = first;
    this.lastName  = rest.join(" ");
  });

// Calculated from other fields
personSchema.virtual("age").get(function () {
  if (!this.dob) return null;
  return Math.floor((Date.now() - this.dob) / (365.25 * 24 * 60 * 60 * 1000));
});
personSchema.virtual("priceWithTax").get(function () { return +(this.price * (1 + this.taxRate)).toFixed(2); });

const Person = mongoose.model("Person", personSchema);
const p = new Person({ firstName: "Asha", lastName: "Verma", dob: "2002-05-10", price: 100 });
p.fullName;             // "Asha Verma"
p.age;                  // e.g. 24
p.priceWithTax;         // 118
p.name = "Ravi Kumar";  // setter splits into firstName="Ravi", lastName="Kumar"
JSON.stringify(p);      // includes fullName, age ... because toJSON.virtuals = true
await p.save();         // only firstName, lastName, dob, price, taxRate are stored

Virtual populate (reverse relationship without storing an array)

const authorSchema = new mongoose.Schema({ name: String }, { toJSON: { virtuals: true } });
const bookSchema   = new mongoose.Schema({ title: String, author: { type: mongoose.Schema.Types.ObjectId, ref: "Author" } });

// An author "has many" books; nothing is stored in the author document
authorSchema.virtual("books", {
  ref: "Book",              // model to query
  localField: "_id",        // field in Author
  foreignField: "author",   // field in Book that holds the author's _id
  justOne: false            // array of books
});

const Author = mongoose.model("Author", authorSchema);
const Book = mongoose.model("Book", bookSchema);
const a = await Author.findOne({ name: "Tagore" }).populate("books");
a.books;                    // [ {title: ...}, ... ]

doc._id;      // ObjectId("665f...")

// Clean JSON output: add "id", remove "_id" and "__v"
schema.set("toJSON", {
  virtuals: true,
  versionKey: false,
  transform: (doc, ret) => { delete ret._id; return ret; }

9. Optimizing Query Performance by Enabling Indexes

Core Concept

An index is a sorted data structure (B-tree) over one or more fields that lets MongoDB find documents without scanning the whole collection. Without an index a query performs a COLLSCAN (reads every document, O(n)); with an index it performs an IXSCAN (about O(log n)). 

 No index on "email":                      Index on "email" (B-tree, sorted):
 COLLSCAN: check doc1, doc2, ... doc1M     IXSCAN: jump ──► "asha@x.com" ──► pointer to doc
 (slow as data grows)                       (milliseconds even for millions of docs)
 Trade-off: indexes speed READS but slow WRITES and use RAM/disk.

Defining indexes in Mongoose

const userSchema = new mongoose.Schema({
  email:    { type: String, required: true, unique: true },   // 1. unique index
  username: { type: String, index: true },                    // 2. single-field index
  city:     String,
  age:      Number,
  bio:      String,
  createdAt:{ type: Date, default: Date.now },
  location: { type: { type: String, enum: ["Point"] }, coordinates: [Number] }
});

// 3. Compound index (field order matters; 1 ascending, -1 descending)
userSchema.index({ city: 1, age: -1 });

// 4. Text index (full-text search; only ONE text index per collection)
userSchema.index({ bio: "text", username: "text" });
// usage: User.find({ $text: { $search: "developer node" } }).sort({ score: { $meta: "textScore" } })

// 5. TTL index (auto-delete documents after N seconds)
userSchema.index({ createdAt: 1 }, { expireAfterSeconds: 3600 });
// or on a field: expires: "1h"

// 6. Unique compound index
userSchema.index({ city: 1, username: 1 }, { unique: true });

// 7. Partial index (index only documents matching a filter; smaller)
userSchema.index({ email: 1 }, { partialFilterExpression: { isActive: true } });

// 8. Sparse index (skip documents lacking the field)
userSchema.index({ phone: 1 }, { sparse: true });

// 9. Geospatial index
userSchema.index({ location: "2dsphere" });

Types of indexes

Index Purpose
Default _id Automatic unique index on every collection
Single field Equality, range, sort on one field
Compound Queries on several fields; supports leftmost-prefix queries
Unique Prevents duplicate values
Text Full-text search
TTL Auto-expire documents (sessions, OTP)

Compound index and the ESR rule

// Index: { city: 1, age: -1 }  supports these:
User.find({ city: "Delhi" });                          // uses prefix "city"
User.find({ city: "Delhi", age: { $gt: 20 } });        // uses both
User.find({ city: "Delhi" }).sort({ age: -1 });        // filter + sort both from the index
User.find({ age: 25 });                                // CANNOT use it (not a leftmost prefix)

// ESR rule for ordering fields in a compound index:
//   E = Equality fields first,  S = Sort fields next,  R = Range fields last
// Query: status == "paid", sort by date, amount > 100  →  index { status:1, date:1, amount:1 }

Index management in Mongoose

// Mongoose builds declared indexes automatically on startup (autoIndex: true by default).
// In production: disable and manage indexes deliberately.
mongoose.connect(uri, { autoIndex: false });         // or schema option { autoIndex: false }

await User.init();                // wait until indexes are built (important in tests: unique checks)
await User.createIndexes();       // create declared indexes now
await User.syncIndexes();         // make DB indexes match the schema (drops extras!)
await User.collection.getIndexes();
await User.collection.dropIndex("city_1_age_-1");

Measuring performance with explain()

const plan = await User.find({ city: "Delhi", age: { $gt: 20 } }).explain("executionStats");
const stats = plan.executionStats;
console.log(stats.executionTimeMillis, stats.totalKeysExamined, stats.totalDocsExamined, stats.nReturned);
// Look at winningPlan.stage:
//   COLLSCAN → full scan (add an index)       IXSCAN → index used (good)
// Ideal: totalDocsExamined ≈ nReturned

// Optimised read endpoint
app.get("/users", async (req, res) => {
  const users = await User.find({ city: req.query.city })   // uses { city:1, age:-1 } index
    .select("name email age")                               // projection
    .sort({ age: -1 })                                      // index-backed sort
    .limit(20)
    .lean();                                                // plain objects
  res.json(users);
});
Key Concept: Index the fields you filter and sort on most. Each extra index slows inserts/updates and consumes memory, so do not index everything. Prove improvements with explain().
Exam Trap:
  • unique: true creates a unique index (E11000 error), not a validator. If duplicates already exist, index creation fails.
  • Compound index order matters; {a:1,b:1} serves queries on a or a+b, but not on b alone (leftmost prefix rule).
  • Indexes are built asynchronously after connect; in tests call await Model.init() before checking uniqueness.
  • Only one text index per collection. A TTL index works only on Date fields and deletes with up to ~60 s delay.
  • syncIndexes() can drop indexes not in the schema; autoIndex should be off for big production collections.
  • Regex without a ^ prefix (or case-insensitive) cannot use an index efficiently. $ne/$nin are poorly indexable.
  • Indexes speed reads and slow writes; too many indexes hurt performance and RAM.
  • COLLSCAN = bad, IXSCAN = good.
