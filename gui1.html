1. Introduction to .NET

Core Concept

.NET is a Microsoft software platform used to build and run applications. It gives developers a runtime, a large class library, and a language-interoperability model.

Technical Breakdown

  • Runtime: executes programs safely (CLR in .NET Framework).
  • Library: reusable code (BCL/FCL).
  • Interoperability: many languages work together through CTS and CLS.
  • Services: Garbage Collection, exception handling, type safety, security.
  • Used for: desktop apps (Windows Forms, WPF), web (ASP.NET), APIs, cloud, mobile.

Why .NET exists: before it, Windows development used COM, OLE and Win32 APIs: powerful but complex, with manual memory management, "DLL Hell" version conflicts and poor cross-language integration. .NET unified all this into one managed environment.

Exam Trap: .NET Framework is the platform; C# is just one language that targets it. VB.NET and F# compile for the same runtime.

2. Origin of .NET: OLE → COM → .NET

2.1 OLE (Object Linking and Embedding)

OLE lets one application embed or link content from another, for example an Excel chart inside a Word document.

  • Embedding: a copy of the object lives inside the document.
  • Linking: the document holds a reference; updating the source file updates the document.
  • Limitation: aimed at document embedding, not general component development; complex to implement. 
 Word Document
   |-- Embed (copy of object) --> [ Embedded Excel Chart ]
   |
   `-- Link (reference only) ---> [ Excel file stays separate ]

2.2 COM (Component Object Model)

COM is a binary standard for reusable components that work across languages (write in C++, use from Visual Basic without recompiling).

  • Interfaces: contracts a component exposes.
  • IUnknown: the base interface with QueryInterface, AddRef, Release.
  • Reference counting: manual-but-systematic memory management.
Exam Trap (Problems in COM): complex interface programming, Windows Registry dependency, DLL Hell (versioning conflicts), manual reference-counting errors causing leaks/crashes, and ActiveX security concerns. These problems motivated .NET.

2.3 .NET Technologies

A managed platform with a runtime (CLR), IL execution, a standard type system (CTS), language rules (CLS), rich libraries (BCL/FCL) and safer deployment via assemblies and metadata.

Feature OLE COM .NET
Main purpose Embed/link objects between apps Build reusable binary components Unified platform to build and run apps
Language interop Limited Strong (binary interfaces) Very strong (CTS + CLS + IL)
Memory management Mostly app-controlled Manual reference counting Automatic GC (managed)
Deployment File-based objects Often registry-based Assemblies + metadata, better versioning

3. Architecture of .NET Framework

Core Concept

Languages (C#, VB.NET, ...) are compiled by language compilers into IL/MSIL, packaged with metadata in an assembly. The CLR loads and executes that IL using the class library (BCL/FCL) and, finally, the OS and hardware.

 +----------------------+-----------------------+
                        v
 +----------------------------------------------+

 |  IL + Metadata + Manifest + Resources        |

Key Concept: Your code is not compiled straight to machine code. It first becomes IL; the CLR makes it run. Different languages interoperate because they share IL and the CTS/CLS.

4. Common Language Runtime (CLR)

Core Concept

The CLR is the execution engine of .NET Framework. It loads assemblies, verifies code, compiles IL to native code, manages memory, handles exceptions, and supports security and threading. Code running under it is called managed code.

CLR service What it does
Managed execution Type safety, stability, standard services
Garbage Collection Objects live on the managed heap; unreferenced objects are reclaimed automatically
Type safety and verification Prevents illegal memory access; can reject unsafe IL
Exception handling try/catch/finally, same behaviour in all .NET languages
Security Code Access Security (CAS), permission checks (historical)
Thread management Thread pool, tasks, locks/monitors 
 Source Code (C#/VB)
      | compile
      v
 IL (MSIL) + Metadata  -> stored in Assembly (.exe/.dll)
      | CLR loads assembly
      v
 Verification + Security checks
      v
 JIT compiles IL method-by-method
      v
 Native Machine Code --> CPU executes --> OS + Hardware

5. Common Type System (CTS)

Core Concept

The CTS defines how types are declared, used and managed so that all .NET languages share one consistent type system. A type written in C# can be used directly in VB.NET. Everything ultimately derives from System.Object.

Category Stored Examples
Value types Directly (often on stack); faster for small data int, double, bool, char, struct, enum
Reference types Reference to heap object; can be null class, string, object, arrays, delegates, interfaces

Boxing/Unboxing: boxing converts a value type to object; unboxing extracts it back. Covered fully in Unit II.

6. Common Language Specification (CLS)

The CLS is a subset of the CTS: a set of rules every .NET language can follow to guarantee interoperability. If a public library uses only CLS-compliant features, any .NET language can consume it. 

[assembly: CLSCompliant(true)]

public class Demo
{
    public uint Bad() { return 1; }   // warning: uint is not CLS-compliant
    public int  Good() { return 1; }  // fine
}
Point CTS CLS
Meaning Full .NET type system Interoperability rule set
Scope Very broad Smaller subset of CTS
Goal Standardize types for the runtime Make libraries usable across languages
Who uses it CLR + all .NET languages Library/API designers
Exam Trap: In public APIs avoid uint (not all languages support unsigned types) and avoid names that differ only by case (Print() vs print()), because some languages are case-insensitive.

7. Microsoft Intermediate Language (MSIL / IL / CIL)

MSIL is the CPU-independent, stack-based instruction set that .NET compilers emit instead of machine code. Along with metadata (type information, references), a manifest and resources, it is packaged into an assembly (.exe / .dll).

Why IL is used Explanation
Portability Runs on different CPUs once JIT-compiled
Language interoperability C#, VB.NET, F# all compile to IL
Verification / security CLR can verify IL before running it
Runtime optimization JIT can optimize for the actual CPU/conditions

8. Just-In-Time (JIT) Compilation

Core Concept

The JIT compiler converts IL into native machine code at run time, typically method by method, the first time each method is called. 

 1. CLR loads assembly
 2. Finds entry point (Main)
 3. IL of needed method --> JIT compiler
 4. JIT --> native machine code
 5. CPU executes native code
 6. Compiled code is CACHED (later calls skip compilation)
  • Benefit: optimized for the actual CPU; only methods that run get compiled.
  • Trade-off: small one-time delay on the first call of each method.
Exam Trap: JIT is lazy. It does not compile the whole program at start-up; a method is compiled only when first invoked.

9. Framework / Base Class Library (BCL / FCL)

A large set of prebuilt, reusable classes so you do not write everything from scratch. BCL is the core set of fundamental classes; FCL is the broader collection (BCL plus extra frameworks). In practice the two terms are used almost interchangeably.

Category Purpose Example use
Collections Store and organize data Student list, attendance map
I/O Work with files Save marksheet to file
Networking Communicate over a network Call an API
Security Protect data Hash a password
XML/JSON Data exchange Read a config file
Threading Parallel work Background processing
UI libraries Build interfaces Windows Forms, WPF, ASP.NET

10. End-to-End Execution in .NET

 Developer
    v
 .NET Language (C#/VB)
    | compile
    v
 IL (MSIL) + Metadata  = Assembly (.exe/.dll)
    | load + verify
    v
 CLR (type safety, CLS rules, GC, security, threads)
    | JIT compile
    v
 Native Machine Code (CPU instruction set)
    | execute
    v
 OS + Hardware
  1. Write code in a .NET language.
  2. Compiler produces IL + metadata packaged as an assembly.
  3. CLR loads the assembly and verifies it (types correct, code safe).
  4. JIT compiles IL to native code, only when a method is needed.
  5. CLR runs it, providing GC, exceptions, security and threading.

11. Tracing a Real Program Through the Pipeline

using System;

class Program
{
    static void Main()
    {
        int a = 5, b = 7;
        Console.WriteLine(a + b);   // prints 12
    }
}
Step What happens
1. Compile csc.exe turns Program.cs into MSIL + metadata, not x86/x64 code
2. Assembly Packaged into Program.exe with a manifest (name, version, references such as mscorlib)
3. Load Windows hands control to the CLR because the exe header says it needs .NET
4. Verify CLR checks IL is type-safe (a + b both int)
5. JIT Just before Main() runs, only its IL becomes native code
6. Execute CPU runs native code; 12 is printed
7. GC Nothing to collect here (value types on stack). A new Student() would live on the managed heap until unreachable
Key Concept: The first call of any method is slower than later calls because it pays the one-time JIT cost.

12. Solved Problem: CTS Type-Compatibility

int x = 10;
long y = x;            // (a) int -> long
long big = 5000000000;
int small = big;       // (b) long -> int
object o = 42;         // (c) int -> object (boxing)
int n = (int)o;        // (d) object -> int (unboxing)
Line Allowed? Reason
(a) Yes, implicit Widening: long can hold every int value
(b) No, needs cast (int)big required; possible data loss must be acknowledged
(c) Yes, implicit boxing Everything derives from System.Object
(d) Explicit cast Unboxing; throws InvalidCastException if the object does not hold an int
