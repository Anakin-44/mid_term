1. Introduction to MongoDB

Core Concept

MongoDB is an open-source, document-oriented NoSQL database (the "M" in MERN). Instead of rows and tables it stores JSON-like documents (internally BSON, Binary JSON) grouped into collections. The name comes from "humongous". It was created by 10gen (now MongoDB Inc.) in 2007 and released in 2009.

Technical Breakdown

  • Schema-flexible: documents in the same collection may have different fields.
  • BSON: binary format that adds types beyond JSON (Date, ObjectId, Decimal128, Binary, Int32/Int64).
  • Rich query language: filters, projections, aggregation pipeline, text and geospatial search.
  • Indexing: single, compound, multikey, text, geospatial, TTL, unique.
  • Replication: replica set (primary + secondaries) gives high availability and automatic failover.
  • Sharding: horizontal scaling by splitting data across servers using a shard key.
  • Transactions: multi-document ACID transactions are supported since 4.0 (replica sets) and 4.2 (sharded clusters).
  • Default port: 27017. Shell: mongosh. Server process: mongod.

              └── Document  { _id, name, price, tags: [...] }   ≈ row

Real-world example: An e-commerce product catalogue: a laptop has RAM and CPU fields, a T-shirt has size and colour. In SQL you need many nullable columns or extra tables; in MongoDB each product document just carries its own fields.

Exam Trap: MongoDB stores BSON, not plain JSON text (but you write queries in JSON-like syntax). "Schemaless" really means flexible schema; you can (and should) still enforce structure with validation or Mongoose. A database or collection is created lazily on first insert.

3. The Current SQL / NoSQL Landscape

Core Concept

SQL (relational) databases store data in tables with a fixed schema, relate them with keys and joins, and guarantee ACID. NoSQL ("Not Only SQL") databases drop the rigid relational model to gain flexible schemas, horizontal scalability and performance for specific workloads. Modern systems are polyglot: one application often uses several kinds of database.

Types of NoSQL Databases

Type Data model Best for Examples
Document JSON/BSON documents in collections Catalogues, CMS, user profiles, APIs MongoDB, CouchDB, Firestore
Key-Value key → opaque value Caching, sessions, counters Redis, DynamoDB, Memcached
Wide-column Rows with dynamic column families Huge write-heavy time-series, IoT Cassandra, HBase
Graph Nodes + edges Social networks, recommendations, fraud Neo4j, Amazon Neptune
Search / Vector Inverted index / embeddings Full-text and AI similarity search Elasticsearch, Pinecone

SQL vs NoSQL (MongoDB)

Aspect SQL (MySQL, PostgreSQL) MongoDB
Structure Tables, rows, columns Collections, documents, fields
Schema Fixed, defined first Flexible (optional validation)
Relationships Foreign keys + JOIN Embedding or references; $lookup
Query language SQL MQL (JSON-style) + aggregation pipeline
Scaling Mostly vertical (bigger server) Horizontal (sharding) built-in
Transactions Strong ACID, mature ACID for multi-document (with some cost); single-document always atomic
Normalisation Normalise, avoid duplication Often denormalise for read speed
Best fit Complex joins, finance, strict integrity Evolving data, hierarchical data, high volume

SQL → MongoDB query translation

-- SQL
SELECT name, age FROM users WHERE age >= 18 AND city = 'Delhi' ORDER BY age DESC LIMIT 5;

// MongoDB
db.users.find({ age: { $gte: 18 }, city: "Delhi" }, { name: 1, age: 1, _id: 0 })
        .sort({ age: -1 }).limit(5);

-- SQL: INSERT INTO users (name, age) VALUES ('Asha', 22);
db.users.insertOne({ name: "Asha", age: 22 });

-- SQL: UPDATE users SET age = 23 WHERE name = 'Asha';
db.users.updateOne({ name: "Asha" }, { $set: { age: 23 } });

-- SQL: DELETE FROM users WHERE name = 'Asha';
db.users.deleteOne({ name: "Asha" });

ACID vs BASE and CAP theorem

ACID (relational) BASE (many NoSQL)
Atomicity: all-or-nothing Basically Available: system stays responsive
Consistency: valid state always Soft state: state may change without input
Isolation: concurrent transactions do not interfere Eventual consistency: replicas converge over time
Durability: committed data survives crashes 
 CAP theorem: a distributed store can guarantee only TWO of three
            Consistency
               /\
              /  \
   CA (RDBMS) /    \ CP  ← MongoDB (default: favours consistency; primary handles writes)
            /______\
   Availability ── Partition tolerance   AP ← Cassandra, DynamoDB
 Partitions (network failures) are unavoidable, so real choice is C vs A.
Key Concept: NoSQL is not "better" than SQL; it is a different trade-off. Choose by data shape and access pattern, not by fashion.
Exam Trap: NoSQL does not mean "no SQL-like querying" and it does not mean "no ACID": MongoDB offers single-document atomicity and multi-document transactions. MongoDB is classified as a CP system in CAP discussions. Joins exist ($lookup) but are not its strength. Do not say MongoDB is "schema-less so no structure needed".

4. Document-Oriented vs Other Types of Storage

Core Concept

A document-oriented database stores each record as a self-describing, hierarchical document that bundles related data together. This contrasts with relational (flattened across tables), key-value (opaque blob per key), column-family and graph storage.

Same data, different storage models

// RELATIONAL: 3 tables, joined at read time
users(id, name)                    orders(id, user_id, date)       order_items(order_id, product, qty)
 1 | Asha                           10 | 1 | 2026-07-01              10 | Pen   | 3
                                                                      10 | Book  | 1

// DOCUMENT: one self-contained document, read in a single operation
{
  _id: 1, name: "Asha",
  orders: [
    { id: 10, date: ISODate("2026-07-01"),
      items: [ { product: "Pen", qty: 3 }, { product: "Book", qty: 1 } ] }
  ]
}

// KEY-VALUE (Redis): value is opaque; you can only fetch by key
SET user:1 '{"name":"Asha"}'      GET user:1
 Relational:   users ──< orders ──< order_items      (joins reconstruct the object)
 Document  :   { user { orders [ { items [ ... ] } ] } }  (object stored as-is: "data that is
                                                           accessed together is stored together")
 Graph     :   (Asha)──BOUGHT──►(Pen)──SIMILAR_TO──►(Marker)

Document Model Design: Embed vs Reference

Embedding (denormalised) Referencing (normalised)
Sub-document or array inside parent Store another document's _id
One read, fast, atomic update Needs second query or $lookup
Use for "contains" / one-to-few (address, comments of a post limited in size) Use for one-to-many large, many-to-many, data shared by many (users ↔ courses)
Risk: 16 MB doc limit, unbounded growth, duplication Risk: extra round trips, no foreign-key enforcement 
// Referencing example
// courses: { _id: "C1", title: "MERN" }
// students: { _id: "S1", name: "Asha", courseIds: ["C1"] }
db.students.aggregate([
  { $lookup: { from: "courses", localField: "courseIds", foreignField: "_id", as: "courses" } }
]);
Storage type Strength Weakness
Document Natural objects, flexible, fast reads, scales out Weaker multi-collection joins, duplication
Relational Integrity, joins, mature tooling Rigid schema, impedance mismatch with objects
Key-value Fastest simple lookups No rich queries
Column-family Massive write throughput Query patterns must be designed up front
Graph Relationship traversal Not for bulk tabular analytics
Key Concept: Design rule for MongoDB: model data according to how the application queries it ("data that is accessed together should be stored together").
Exam Trap: A document database is not a file/document store like PDFs; "document" means a structured JSON-like record. Embedding unbounded arrays (e.g., every log entry in one document) hits the 16 MB limit and hurts performance. Normalising everything like SQL defeats MongoDB's advantage.

5. MongoDB Databases

Core Concept

A database is a physical container for collections. One MongoDB server can host many databases, each with its own files and permissions.

Built-in databases

Name Purpose
admin Administration, users and roles; special commands run here
local Server-local data such as the replication oplog; never replicated
config Sharded-cluster metadata
test Default db a bare mongosh session starts in

Database commands

show dbs                       // list databases (only non-empty ones appear)
db                             // print the CURRENT database name
use shopDB                     // switch to shopDB (created lazily on first write!)
db.getName()
db.stats()                     // size, collections, indexes
db.dropDatabase()              // permanently deletes the CURRENT database
db.getSiblingDB("other")       // reference another db without switching
db.runCommand({ listDatabases: 1 })

// Example of lazy creation
use blogDB                     // switched, but not yet on disk
show dbs                       // blogDB NOT listed
db.posts.insertOne({ title: "Hi" })   // first write creates database + collection
show dbs                       // blogDB now appears
// Node.js driver
const db = client.db("shopDB");
const dbs = await client.db().admin().listDatabases();
await db.dropDatabase();

Naming rules

  • Case-sensitive; max 64 characters; cannot be empty.
  • Cannot contain: / \ . " $ * < > : | ? space or null character.
  • Avoid reserved names admin, local, config. Lower-case is convention (on Windows names differing only by case clash). 
 mongod
  ├── admin
  ├── local
  ├── config
  ├── shopDB   ── products, orders, users
  └── blogDB   ── posts, comments
Exam Trap: use dbname does not create the database; the first insert does. show dbs hides empty databases. db.dropDatabase() drops whichever database you are currently in, so check with db first. Database names are case-sensitive (Shop ≠ shop).

6. MongoDB Collections

Core Concept

A collection is a group of documents inside a database (analogous to a table). Collections do not enforce a schema by default, but documents are normally related by purpose (e.g., users, products). 

use shopDB

// Implicit creation: on first insert
db.products.insertOne({ name: "Pen", price: 10 });

// Explicit creation with options
db.createCollection("orders");

// Capped collection: fixed size, FIFO, insertion order kept (logs, caches)
db.createCollection("logs", { capped: true, size: 1048576, max: 5000 });

// Collection with schema validation
db.createCollection("students", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["name", "age"],
      properties: {
        name: { bsonType: "string", description: "must be a string" },
        age:  { bsonType: "int", minimum: 16, maximum: 60 },
        email:{ bsonType: "string", pattern: "^.+@.+$" }
      }
    }
  },
  validationLevel: "strict",     // or "moderate"
  validationAction: "error"      // or "warn"
});

show collections                 // list collections in the current db
db.getCollectionNames()
db.products.countDocuments()     // exact count
db.products.estimatedDocumentCount()   // fast, from metadata
db.products.stats()
db.products.renameCollection("items")
db.products.drop()               // delete the collection (+ its indexes)

// Time-series collection (sensor data)
db.createCollection("sensor", { timeseries: { timeField: "ts", metaField: "deviceId" } });
Collection type Feature
Standard Default, unlimited growth
Capped Fixed size; oldest documents overwritten; cannot delete individual documents
Time-series Optimised for timestamped measurements
View Read-only virtual collection from an aggregation pipeline (db.createView())
Validated Has $jsonSchema rules

Collection naming rules

  • Must begin with a letter or underscore; cannot be empty; cannot contain $ or the null character.
  • Cannot start with system. (reserved). Use plural lowercase names by convention (users).
  • Mongoose automatically pluralises and lower-cases model names (User → users). 
 shopDB
  ├── products   [ {..}, {..}, {..} ]   ← documents need NOT share identical fields
  ├── orders     [ {..}, {..} ]
  └── logs (capped, 1 MB)  [ oldest ◄──────────── newest ]  ring buffer
Exam Trap: Collections are created on first insert too. In a capped collection you cannot remove single documents or grow beyond the size; oldest entries are overwritten automatically. drop() removes the whole collection, whereas deleteMany({}) removes documents but keeps the collection and its indexes. Schema validation applies only to new inserts/updates unless validationLevel says otherwise.

7. MongoDB Documents

Core Concept

A document is an ordered set of field : value pairs, stored as BSON; it is the basic unit of data in MongoDB. Maximum size is 16 MB (use GridFS for larger files). 

{
  _id: ObjectId("665f1c2a9b1e8a3d4c5e6f70"),     // primary key (auto-generated if omitted)
  name: "Asha",                                    // string
  age: 22,                                         // number
  isActive: true,                                  // boolean
  marks: [78, 85, 91],                             // array
  address: { city: "Dehradun", pin: "248001" },    // embedded document
  joined: new Date("2026-07-01"),                  // date
  cgpa: Decimal128("8.75"),                        // exact decimal
  photo: null                                      // null
}

BSON Data Types

Type Example Notes
String "hello" UTF-8
Int32 / Int64 / Double NumberInt(5), NumberLong(5), 3.14 Shell default for plain numbers is Double
Decimal128 Decimal128("9.99") Use for money
Boolean true
Date new Date(), ISODate() UTC milliseconds
ObjectId ObjectId() 12-byte unique id
Array [1,2,3] Can mix types
Object (embedded) {a:1} Nesting up to 100 levels
Null, Regex, Binary, Timestamp, MinKey/MaxKey Special types

The _id field and ObjectId

  • Every document must have a unique _id; it is the primary key and is automatically indexed (unique).
  • If omitted, MongoDB generates an ObjectId. You may supply your own (number, string, UUID) but it must be unique and immutable. 
 ObjectId = 12 bytes = 24 hex characters
 ┌────────────────┬──────────────────┬──────────────┐
 │ 4 bytes        │ 5 bytes          │ 3 bytes      │
 │ timestamp(sec) │ random per-process│ incrementing │
 │                │ value            │ counter      │
 └────────────────┴──────────────────┴──────────────┘
 Roughly time-ordered; ObjectId().getTimestamp() returns creation date.

const id = new ObjectId();
id.getTimestamp();                      // creation date
id.toString();                          // "665f1c2a..."
db.users.findOne({ _id: ObjectId("665f1c2a9b1e8a3d4c5e6f70") });  // must wrap string!

// Field name rules
// - strings; cannot contain the null character
// - should not start with "$" and should avoid "." (dot is used for nested paths)
// - field order is preserved; duplicate names are not allowed

Dot notation (embedded fields and arrays)

db.users.find({ "address.city": "Dehradun" });   // embedded field
db.users.find({ "marks.0": 78 });                // array element by index
// Quotes are required around dotted names
JSON BSON
Text format Binary format
Limited types (string, number, bool, null, array, object) Adds Date, ObjectId, Decimal128, Binary, Int32/64...
Human-readable Machine-efficient, traversable (stores lengths)
Exam Trap: A string id is not an ObjectId: find({_id: "665f..."}) returns nothing; wrap it with ObjectId("..."). _id cannot be changed after insertion. Plain numbers in the shell are stored as Double, so use NumberInt / Decimal128 where type matters (and for money avoid float). Max document size is 16 MB; max nesting depth 100.

8. CRUD Operations in MongoDB

Core Concept

CRUD = Create, Read, Update, Delete: the four fundamental data operations. Every one targets a collection and (except create) uses a filter document to choose which documents are affected.

Operation Modern methods SQL equivalent Returns
Create insertOne(), insertMany() INSERT {acknowledged, insertedId(s)}
Read find(), findOne() SELECT Cursor / one document
Update updateOne(), updateMany(), replaceOne() UPDATE {matchedCount, modifiedCount, upsertedId}
Delete deleteOne(), deleteMany() DELETE {deletedCount}

End-to-end walkthrough (mongosh)

use school

// CREATE
db.students.insertOne({ name: "Asha", age: 22, course: "MCA", marks: [78, 85] });
db.students.insertMany([
  { name: "Ravi",  age: 24, course: "MCA", marks: [66, 72] },
  { name: "Meera", age: 21, course: "BCA", marks: [90, 88] }
]);

// READ
db.students.find();                                  // all
db.students.find({ course: "MCA" });                 // filter
db.students.findOne({ name: "Asha" });               // first match
db.students.find({ age: { $gt: 21 } }, { name: 1, _id: 0 });   // projection

// UPDATE
db.students.updateOne({ name: "Asha" }, { $set: { age: 23 } });
db.students.updateMany({ course: "MCA" }, { $inc: { age: 1 } });

// DELETE
db.students.deleteOne({ name: "Ravi" });
db.students.deleteMany({ course: "BCA" });

Same CRUD in an Express REST API (Node driver)

const { MongoClient, ObjectId } = require("mongodb");
const students = client.db("school").collection("students");

app.post("/students", async (req, res) => {                       // CREATE
  const r = await students.insertOne(req.body);
  res.status(201).json({ _id: r.insertedId });
});
app.get("/students", async (req, res) => {                        // READ
  res.json(await students.find().toArray());                       // cursor → array
});
app.put("/students/:id", async (req, res) => {                    // UPDATE
  const r = await students.updateOne({ _id: new ObjectId(req.params.id) }, { $set: req.body });
  res.json({ matched: r.matchedCount, modified: r.modifiedCount });
});
app.delete("/students/:id", async (req, res) => {                 // DELETE
  const r = await students.deleteOne({ _id: new ObjectId(req.params.id) });
  res.json({ deleted: r.deletedCount });
});
 HTTP verb   CRUD     Mongo method                 Result
 POST        Create   insertOne / insertMany       insertedId
 GET         Read     find / findOne               documents
 PUT/PATCH   Update   updateOne / replaceOne       matchedCount, modifiedCount
 DELETE      Delete   deleteOne / deleteMany       deletedCount
Exam Trap: find() returns a cursor, not an array; in Node call .toArray() (and it is lazy: shell shows only 20 documents, type it for more). matchedCount vs modifiedCount differ when the new value equals the old one. All single-document operations are atomic. Writes are acknowledged by default (w: 1).

9. MongoDB Methods: insert(), update(), save(), find(), delete()

The syllabus names the classic method names. Modern MongoDB (drivers and mongosh) prefers the specific *One / *Many forms. Both are explained below.

Legacy (syllabus) Status Modern replacement
insert() Deprecated insertOne() / insertMany()
update() Deprecated updateOne() / updateMany() / replaceOne()
save() Deprecated; removed from mongosh insertOne() or replaceOne(..., {upsert:true})
find() Current (unchanged) + findOne()
remove() / "delete" remove() deprecated deleteOne() / deleteMany()

9.1 insert()

// Legacy: accepts a document OR an array
db.users.insert({ name: "Asha" });
db.users.insert([{ name: "A" }, { name: "B" }]);

// Modern
db.users.insertOne({ name: "Asha", age: 22 });
// → { acknowledged: true, insertedId: ObjectId("...") }

db.users.insertMany([{ name: "Ravi" }, { name: "Meera" }]);
// → { acknowledged: true, insertedIds: { '0': ObjectId(...), '1': ObjectId(...) } }

// Custom _id; duplicate _id → E11000 duplicate key error
db.users.insertOne({ _id: 101, name: "Custom" });

// ordered: true (default) stops at first error; false continues with the rest
db.users.insertMany([{_id:1},{_id:1},{_id:2}], { ordered: false });

9.2 find()

db.users.find()                         // all documents (cursor)
db.users.find({ age: 22 })              // filter
db.users.findOne({ name: "Asha" })      // single document or null

// Projection (2nd argument): 1 = include, 0 = exclude (cannot mix, except _id)
db.users.find({}, { name: 1, age: 1 });          // _id included by default
db.users.find({}, { name: 1, _id: 0 });
db.users.find({}, { password: 0 });              // hide one field

// Cursor modifiers (chainable)
db.users.find().sort({ age: -1, name: 1 })       // 1 ascending, -1 descending
db.users.find().limit(5)
db.users.find().skip(10).limit(5)                // pagination: page 3 of size 5
db.users.find().count()                          // deprecated → use countDocuments(filter)
db.users.countDocuments({ age: { $gt: 20 } })
db.users.distinct("course")                      // unique values of a field
db.users.find().pretty()                         // legacy shell only (mongosh pretty-prints)
db.users.find().explain("executionStats")        // query plan

// Node driver
const list = await users.find({ age: { $gt: 20 } }).project({ name: 1 }).sort({ age: -1 }).limit(10).toArray();

9.3 update()

// Legacy update(query, update, options)
db.users.update({ name: "Asha" }, { $set: { age: 23 } });                     // ONE doc (default)
db.users.update({ course: "MCA" }, { $set: { year: 2 } }, { multi: true });   // ALL matches
db.users.update({ name: "Zed" }, { $set: { age: 30 } }, { upsert: true });    // insert if none

// DANGER (legacy): update WITHOUT an operator REPLACES the whole document
db.users.update({ name: "Asha" }, { age: 25 });      // doc becomes { _id, age: 25 } !!

// Modern, safer
db.users.updateOne({ name: "Asha" }, { $set: { age: 23 } });
db.users.updateMany({ course: "MCA" }, { $set: { year: 2 } });
db.users.replaceOne({ name: "Asha" }, { name: "Asha", age: 25 });   // explicit full replace
// Result: { acknowledged, matchedCount, modifiedCount, upsertedId, upsertedCount }

9.4 save() (legacy)

save(doc) was a shortcut: if the document has an _id that exists → replace it; otherwise → insert it. It is removed from mongosh. 

// Legacy mongo shell behaviour
db.users.save({ name: "New" });                       // no _id → INSERT
db.users.save({ _id: 101, name: "Changed", age: 30 }); // _id exists → REPLACE whole doc
                                                       // _id not found → INSERT with that _id

// Modern equivalents
db.users.insertOne({ name: "New" });
db.users.replaceOne({ _id: 101 }, { name: "Changed", age: 30 }, { upsert: true });

9.5 delete() / remove()

// There is no db.collection.delete(); the methods are:
db.users.deleteOne({ name: "Asha" });      // first match only → { acknowledged, deletedCount: 1 }
db.users.deleteMany({ age: { $lt: 18 } }); // all matches
db.users.deleteMany({});                    // ALL documents (collection and indexes remain)

// Legacy
db.users.remove({ name: "Asha" });                  // removes ALL matches by default
db.users.remove({ name: "Asha" }, { justOne: true });
db.users.remove({});                                // all documents
 save(doc):                         update(q, u):
   has _id? ──no──► INSERT            u has $operators? ─yes─► MODIFY fields
      │yes                                   │no
      ▼                                      ▼
   _id exists? ─yes─► REPLACE doc        REPLACE entire document (keeps _id)
      │no ─► INSERT
Exam Trap (very high-yield):
  • Legacy update() changes only one document unless {multi:true}; legacy remove() deletes all matches unless {justOne:true} (opposite defaults!).
  • update(filter, {age: 25}) without $set replaces the document; this is the classic data-loss mistake. updateOne rejects a document without operators.
  • save() = insert-or-replace based on _id; it does not merge fields.
  • insertMany: ordered:true stops at first failure; ordered:false continues.
  • Projection cannot mix inclusion and exclusion (except _id: 0).
  • There is no db.collection.delete(); use deleteOne/deleteMany.

10. Working with Equality

Core Concept

The simplest query is an equality match: { field: value } returns documents where the field equals the value. It is shorthand for { field: { $eq: value } }. Multiple fields in one filter are combined with an implicit AND. 

// Sample data
db.people.insertMany([
  { _id: 1, name: "Asha", age: 22, city: "Delhi",  tags: ["js", "node"], address: { city: "Delhi", pin: "110001" }, phone: null },
  { _id: 2, name: "Ravi", age: 24, city: "Pune",   tags: ["java"],       address: { city: "Pune",  pin: "411001" } },
  { _id: 3, name: "Meera",age: 22, city: "Delhi",  tags: ["node", "js"], address: { pin: "110002", city: "Delhi" } }
]);

// 1. Basic equality
db.people.find({ name: "Asha" });                 // = { name: { $eq: "Asha" } }

// 2. Multiple conditions = implicit AND
db.people.find({ age: 22, city: "Delhi" });       // _id 1 and 3

// 3. Embedded document: EXACT match (field order and all fields matter!)
db.people.find({ address: { city: "Delhi", pin: "110001" } });   // matches _id 1 ONLY
db.people.find({ address: { pin: "110002", city: "Delhi" } });   // matches _id 3 only (order differs)
db.people.find({ address: { city: "Delhi" } });                  // matches NOTHING (not exact)

// 3b. Dot notation: match one embedded field (preferred)
db.people.find({ "address.city": "Delhi" });                     // _id 1 and 3

// 4. Array equality
db.people.find({ tags: "node" });                 // array CONTAINS "node" → _id 1 and 3
db.people.find({ tags: ["node", "js"] });         // EXACT array, same order → _id 3 only
db.people.find({ "tags.0": "js" });               // first element is "js" → _id 1
db.people.find({ tags: { $size: 2 } });           // array length

// 5. null matches null AND missing fields
db.people.find({ phone: null });                  // _id 1 (null) + _id 2, 3 (field missing)
db.people.find({ phone: { $exists: false } });    // only 2 and 3 (field absent)
db.people.find({ phone: { $type: "null" } });     // only 1 (explicit null)

// 6. _id equality needs ObjectId for auto ids
db.people.find({ _id: 2 });                       // custom numeric _id here
db.users.find({ _id: ObjectId("665f1c2a9b1e8a3d4c5e6f70") });

// 7. Type matters: no automatic coercion
db.people.find({ age: "22" });                    // nothing (string ≠ number)

// 8. Case-sensitive strings
db.people.find({ city: "delhi" });                // nothing
db.people.find({ city: /^delhi$/i });             // case-insensitive via regex

// 9. Explicit $eq (needed inside operators like $and/$or/aggregation)
db.people.find({ $and: [{ age: { $eq: 22 } }, { city: { $eq: "Delhi" } }] });
Query What it really means
{ tags: "node" } Array contains element "node"
{ tags: ["node","js"] } Array equals exactly this array (order matters)
{ address: {city:"Delhi"} } Embedded doc equals exactly this doc
{ "address.city": "Delhi" } That one field equals "Delhi"
{ phone: null } null OR field does not exist
Key Concept: Equality on a field that holds an array succeeds if any element equals the value, unless you pass the whole array (then it must match exactly).
Exam Trap: Embedded document equality is exact and order-sensitive; use dot notation instead. {field: null} also matches documents where the field is missing. "22" ≠ 22. String comparison is case-sensitive. Dotted field names must be in quotes. Two same keys in one filter object ({age:20, age:30}) overwrite each other; use $or/$and.

11. Query Operators

Core Concept

Query operators start with $ and let a filter express more than equality: comparison, logic, existence, patterns and array conditions. Syntax: { field: { $operator: value } }.

Comparison operators

Operator Meaning Example
$eq Equal { age: { $eq: 22 } }
$ne Not equal (also matches missing field) { city: { $ne: "Delhi" } }
$gt / $gte Greater than / or equal { age: { $gte: 18 } }
$lt / $lte Less than / or equal { price: { $lt: 500 } }
$in Equals any value in the list { city: { $in: ["Delhi","Pune"] } }
$nin Equals none (also missing field) { city: { $nin: ["Delhi"] } } 
db.people.find({ age: { $gte: 22, $lte: 30 } });            // range: 22..30 (same field, both ops in one object)
db.people.find({ city: { $in: ["Delhi", "Pune"] } });
db.people.find({ name: { $in: [/^A/, /^R/] } });            // $in accepts regex too

Logical operators

Operator Meaning
$and All conditions true (implicit when comma-separated on different fields)
$or At least one condition true
$nor None of the conditions true
$not Inverts one operator expression on a field 
db.people.find({ $or: [{ city: "Delhi" }, { age: { $gt: 23 } }] });
db.people.find({ $and: [{ age: { $gt: 20 } }, { age: { $lt: 25 } }] });
db.people.find({ $nor: [{ city: "Pune" }, { age: 30 }] });
db.people.find({ age: { $not: { $gt: 22 } } });             // age ≤ 22 OR age missing
// $and is REQUIRED when the same key/operator repeats:
db.people.find({ $and: [{ $or: [{a:1},{b:2}] }, { $or: [{c:3},{d:4}] }] });

Element operators

db.people.find({ phone: { $exists: true } });        // field present (even if null)
db.people.find({ age: { $type: "number" } });        // by BSON type name or number
db.people.find({ _id: { $type: "objectId" } });

Evaluation operators

db.people.find({ name: { $regex: "^a", $options: "i" } });     // or { name: /^a/i }
db.people.find({ age: { $mod: [2, 0] } });                      // even ages (age % 2 == 0)
db.people.find({ $expr: { $gt: ["$spent", "$budget"] } });      // compare two fields
db.articles.find({ $text: { $search: "mongodb tutorial" } });   // needs a text index
db.people.find({ $where: "this.age > 20" });                   // JS expression: SLOW, avoid

Array operators

Operator Meaning
$all Array contains all listed elements (any order)
$elemMatch One single element satisfies all given conditions
$size Array has exactly this length 
db.people.find({ tags: { $all: ["js", "node"] } });            // both present
db.people.find({ tags: { $size: 2 } });

// $elemMatch vs plain conditions
// scores: [ {sub:"math", mark:90}, {sub:"sci", mark:40} ]
db.exams.find({ scores: { $elemMatch: { sub: "math", mark: { $gt: 80 } } } });  // SAME element
db.exams.find({ "scores.sub": "math", "scores.mark": { $lt: 50 } });            // can match DIFFERENT elements!

Projection and cursor helpers

db.exams.find({}, { scores: { $slice: 2 } });            // first 2 array items
db.exams.find({ "scores.sub": "math" }, { "scores.$": 1 }); // first matching element only
 Operator families
  Comparison : $eq $ne $gt $gte $lt $lte $in $nin
  Logical    : $and $or $nor $not
  Element    : $exists $type
  Evaluation : $regex $mod $expr $text $where $jsonSchema
  Array      : $all $elemMatch $size
  Geospatial : $near $geoWithin $geoIntersects
  Bitwise    : $bitsAllSet ...
Exam Trap: Several conditions on one field go in one object: {age:{$gt:20,$lt:30}}; repeating the key {age:{$gt:20}, age:{$lt:30}} keeps only the last. $ne and $nin also return documents where the field is missing. $or takes an array of conditions. $and is implicit for different fields. $not wraps an operator expression ({age:{$not:{$gt:5}}}), it is not a top-level logical like $nor. $elemMatch forces conditions to hit the same array element.

12. Building Complex Queries

Core Concept

Complex queries combine operators, nested logic, embedded paths, projection, sorting, pagination and aggregation to answer real business questions. Build them step by step: start with the simplest filter, then add conditions, test, then add sort/limit/projection.

Step-by-step construction (example: products collection)

// Goal: "Electronics OR Books, priced 100–5000, in stock, rating ≥ 4,
//        not 'Refurbished', show name+price, cheapest first, 10 per page (page 2)"

db.products.find(
  {
    category: { $in: ["Electronics", "Books"] },          // 1. membership
    price:    { $gte: 100, $lte: 5000 },                   // 2. range
    stock:    { $gt: 0 },                                   // 3. availability
    "ratings.avg": { $gte: 4 },                             // 4. embedded field (dot notation)
    condition: { $ne: "Refurbished" },                      // 5. exclusion
    $or: [                                                  // 6. either/or branch
      { brand: "Sony" },
      { tags: { $all: ["wireless", "bluetooth"] } }
    ]
  },
  { name: 1, price: 1, _id: 0 }                             // 7. projection
).sort({ price: 1, name: 1 })                               // 8. sort (cheapest first)
 .skip(10).limit(10);                                       // 9. pagination (page 2)

More patterns

// Nested AND/OR
db.users.find({ $and: [
  { $or: [{ city: "Delhi" }, { city: "Pune" }] },
  { $or: [{ age: { $lt: 18 } }, { age: { $gt: 60 } }] }
]});

// Date range (last 7 days)
const since = new Date(Date.now() - 7 * 24 * 60 * 60 * 1000);
db.orders.find({ createdAt: { $gte: since } });

// Search / autocomplete (case-insensitive prefix)
db.users.find({ name: { $regex: "^as", $options: "i" } });

// Array of objects: same-element match
db.orders.find({ items: { $elemMatch: { product: "Pen", qty: { $gte: 3 } } } });

// Fields that exist and are non-empty
db.users.find({ email: { $exists: true, $ne: "" } });

// Compare two fields of the same doc
db.accounts.find({ $expr: { $lt: ["$balance", "$minBalance"] } });

// Top 3 highest marks
db.students.find().sort({ marks: -1 }).limit(3);

// Dynamic filter built in Express from query string
app.get("/products", async (req, res) => {
  const { category, min, max, q, page = 1, limit = 10, sort = "price" } = req.query;
  const filter = {};
  if (category) filter.category = category;
  if (min || max) filter.price = { ...(min && { $gte: +min }), ...(max && { $lte: +max }) };
  if (q) filter.name = { $regex: q, $options: "i" };
  const data = await products.find(filter)
    .sort({ [sort]: 1 })
    .skip((page - 1) * limit).limit(+limit).toArray();
  res.json(data);
});

Aggregation pipeline (for grouping and reports)

// Total sales and average order value per city, only cities with total > 10000
db.orders.aggregate([
  { $match:  { status: "paid" } },                                   // 1. filter (like WHERE)
  { $group:  { _id: "$city", total: { $sum: "$amount" },
               avg: { $avg: "$amount" }, count: { $sum: 1 } } },     // 2. GROUP BY
  { $match:  { total: { $gt: 10000 } } },                            // 3. HAVING
  { $sort:   { total: -1 } },                                        // 4. ORDER BY
  { $limit:  5 },                                                    // 5. LIMIT
  { $project:{ _id: 0, city: "$_id", total: 1, avg: { $round: ["$avg", 2] } } }
]);

// Join with $lookup
db.orders.aggregate([
  { $lookup: { from: "users", localField: "userId", foreignField: "_id", as: "user" } },
  { $unwind: "$user" }
]);
Stage SQL analogue
$match WHERE / HAVING
$group GROUP BY + aggregates
$project SELECT columns / expressions
$sort, $limit, $skip ORDER BY, LIMIT, OFFSET
$lookup LEFT JOIN
$unwind Flatten an array into rows

Making queries fast: indexes and explain

db.products.createIndex({ category: 1, price: 1 });          // compound index (order matters)
db.users.createIndex({ email: 1 }, { unique: true });
db.products.getIndexes();
db.products.find({ category: "Books" }).explain("executionStats");
// Good: stage IXSCAN, totalDocsExamined ≈ nReturned
// Bad : stage COLLSCAN (scans every document)
 Aggregation pipeline (documents flow left → right)
 collection ─► $match ─► $group ─► $match ─► $sort ─► $limit ─► $project ─► result
 Put $match and $limit EARLY to reduce the data flowing through.
Key Concept: Logical order of cursor modifiers is always sort → skip → limit, regardless of the order you chain them. Large skip() values are slow; for deep pagination use a range filter on an indexed field (e.g., _id > lastId).
Exam Trap: Conditions on different fields are ANDed automatically, but $or must be an array. Unindexed queries cause a COLLSCAN. Regex that does not start with ^ or uses i cannot use an index efficiently. Query-string values are strings; convert with Number() before comparing to numbers. Never pass raw req.body as a filter (NoSQL injection, e.g., {"password": {"$ne": null}}); validate and sanitise input. In compound index {a:1,b:1} the leftmost prefix rule applies.

13. Updating Documents

Core Concept

Updating changes existing documents in place using update operators so you modify only chosen fields instead of replacing the whole document. Syntax: updateOne(filter, update, options).

Field update operators

Operator Effect Example
$set Set / add field value { $set: { age: 23, "address.city": "Pune" } }
$unset Remove field { $unset: { phone: "" } }
$inc Increment (negative to decrement) { $inc: { stock: -1, views: 1 } }
$mul Multiply { $mul: { price: 1.1 } }
$min / $max Update only if new value is smaller / larger { $max: { highScore: 95 } }
$rename Rename a field { $rename: { fname: "firstName" } }
$currentDate Set to current date/timestamp { $currentDate: { updatedAt: true } }
$setOnInsert Set only when upsert inserts { $setOnInsert: { createdAt: new Date() } }

Array update operators

Operator Effect
$push Append element (with $each, $position, $slice, $sort)
$addToSet Append only if not already present (unique)
$pull Remove all elements matching a condition
$pullAll Remove all listed values
$pop Remove first (-1) or last (1) element
$, $[], $[id] Positional: first match / all elements / filtered elements 
// Basic
db.users.updateOne({ name: "Asha" }, { $set: { age: 23, city: "Pune" } });
db.users.updateMany({ city: "Delhi" }, { $set: { zone: "North" } });
db.users.updateOne({ name: "Asha" }, { $unset: { phone: "" } });
db.products.updateOne({ _id: 1 }, { $inc: { stock: -1 }, $currentDate: { updatedAt: true } });

// Multiple operators in one atomic update
db.users.updateOne({ _id: 1 }, {
  $set:   { status: "active" },
  $inc:   { loginCount: 1 },
  $push:  { logins: new Date() }
});

// Arrays
db.users.updateOne({ _id: 1 }, { $push: { tags: "mongodb" } });
db.users.updateOne({ _id: 1 }, { $push: { tags: { $each: ["a", "b"], $slice: -5 } } }); // keep last 5
db.users.updateOne({ _id: 1 }, { $addToSet: { tags: "node" } });                         // no duplicates
db.users.updateOne({ _id: 1 }, { $pull: { tags: "old" } });
db.users.updateOne({ _id: 1 }, { $pop: { tags: 1 } });

// Positional operators
db.exams.updateOne({ _id: 1, "scores.sub": "math" }, { $set: { "scores.$.mark": 95 } });   // first match
db.exams.updateOne({ _id: 1 }, { $inc: { "scores.$[].mark": 5 } });                         // ALL elements
db.exams.updateOne({ _id: 1 }, { $set: { "scores.$[e].grade": "A" } },
                   { arrayFilters: [{ "e.mark": { $gte: 90 } }] });                         // filtered elements

// Upsert: update if found, otherwise insert
db.counters.updateOne({ _id: "visits" }, { $inc: { n: 1 }, $setOnInsert: { since: new Date() } }, { upsert: true });

// Replace a whole document (keeps _id)
db.users.replaceOne({ _id: 1 }, { name: "Asha", age: 25 });

// Pipeline-style update (reference other fields)
db.orders.updateMany({}, [{ $set: { total: { $multiply: ["$price", "$qty"] } } }]);

// Get the document back (atomic read-modify-write)
db.users.findOneAndUpdate({ name: "Asha" }, { $inc: { age: 1 } }, { returnDocument: "after" });

Result object

{ acknowledged: true,
  matchedCount: 1,      // documents that matched the filter
  modifiedCount: 1,     // documents actually changed (0 if value was already the same)
  upsertedId: null,     // _id of inserted doc when upsert created one
  upsertedCount: 0 }

Express update route

app.patch("/users/:id", async (req, res) => {
  const { name, age } = req.body;                     // whitelist fields; never spread raw body blindly
  const r = await users.updateOne({ _id: new ObjectId(req.params.id) }, { $set: { name, age } });
  if (r.matchedCount === 0) return res.status(404).json({ error: "Not found" });
  res.json({ modified: r.modifiedCount });
});
Method Scope Replaces whole doc?
updateOne First match No (needs operators)
updateMany All matches No (needs operators)
replaceOne First match Yes (except _id)
findOneAndUpdate First match, returns doc No
Key Concept: A multi-operator update on one document is atomic, so counters like $inc are safe under concurrency (unlike read → modify → save in application code).
Exam Trap: Forgetting $set in legacy update() replaces the whole document. _id cannot be modified. $set on a missing field creates it. $push allows duplicates; $addToSet does not. modifiedCount can be 0 even when matchedCount is 1. $ updates only the first matching array element; use $[] for all. You cannot use the same field in two operators in one update (conflict error). upsert with _id-less filters generates a new ObjectId. Using $inc on a non-numeric field throws an error.

14. Deleting Documents

Core Concept

Deletion permanently removes documents that match a filter. Deletes are irreversible (no recycle bin), so always test the filter with find() first. 

// Preview what would be deleted
db.users.find({ status: "inactive" });
db.users.countDocuments({ status: "inactive" });

// Delete ONE (first match)
db.users.deleteOne({ name: "Asha" });
// → { acknowledged: true, deletedCount: 1 }

// Delete MANY
db.users.deleteMany({ status: "inactive" });
db.users.deleteMany({ createdAt: { $lt: new Date("2025-01-01") } });

// Delete by _id (most common in APIs)
db.users.deleteOne({ _id: ObjectId("665f1c2a9b1e8a3d4c5e6f70") });

// Delete ALL documents (collection + indexes stay)
db.users.deleteMany({});

// Delete and return the removed document
db.users.findOneAndDelete({ name: "Ravi" });

// Legacy
db.users.remove({ name: "Asha" });                       // removes ALL matches
db.users.remove({ name: "Asha" }, { justOne: true });    // only first

// Remove only part of a document → that is an UPDATE, not a delete
db.users.updateOne({ _id: 1 }, { $unset: { phone: "" } });         // delete a field
db.users.updateOne({ _id: 1 }, { $pull: { tags: "old" } });        // delete an array element

// Drop whole collection / database
db.users.drop();               // removes collection AND its indexes (fast)
db.dropDatabase();

Express DELETE route

app.delete("/users/:id", async (req, res) => {
  if (!ObjectId.isValid(req.params.id)) return res.status(400).json({ error: "Invalid id" });
  const r = await users.deleteOne({ _id: new ObjectId(req.params.id) });
  if (r.deletedCount === 0) return res.status(404).json({ error: "Not found" });
  res.sendStatus(204);                                   // 204 No Content
});

Safer alternatives

// 1. Soft delete: mark instead of removing (can restore, keep audit trail)
db.users.updateOne({ _id: 1 }, { $set: { isDeleted: true, deletedAt: new Date() } });
db.users.find({ isDeleted: { $ne: true } });             // normal queries hide them

// 2. TTL index: MongoDB auto-deletes documents after a time (sessions, OTPs, logs)
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 });   // 1 hour
// (the TTL monitor runs about once a minute, so deletion is not instant)

// 3. Transaction for multi-collection deletes (replica set / Atlas)
const session = client.startSession();
await session.withTransaction(async () => {
  await db.collection("orders").deleteMany({ userId: 1 }, { session });
  await db.collection("users").deleteOne({ _id: 1 }, { session });
});
Goal Use Collection / indexes kept?
Delete one document deleteOne(filter) Yes
Delete matching documents deleteMany(filter) Yes
Empty the collection deleteMany({}) Yes
Remove the collection itself drop() No
Remove the database dropDatabase() No
Remove one field updateOne + $unset (update, not delete) 
 deleteOne({..})      → removes 1 document
 deleteMany({..})     → removes all matching documents
 deleteMany({})       → collection becomes empty (still exists, indexes remain)
 drop()               → collection gone (also its indexes)       ← faster for clearing everything
 dropDatabase()       → entire database gone
Exam Trap: deleteMany({}) with an empty filter wipes every document; a typo that yields {} (e.g., an undefined variable in a filter object) is a classic production disaster. deleteOne removes only the first match, and "first" is not guaranteed to be the oldest unless you control it with a unique filter like _id. Legacy remove() deletes all matches by default. Deleting documents from a capped collection is not allowed. deletedCount: 0 is not an error; check it to return 404. Always validate ObjectId strings with ObjectId.isValid() to avoid a 500 error. There is no undo: back up with mongodump or use soft delete.
