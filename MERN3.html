1. Introduction to React

Core Concept

React is an open-source, declarative, component-based JavaScript library for building user interfaces (the "R" in MERN). It was created at Facebook (Meta) and released in 2013. It is a library focused on the View layer, not a full framework.

Technical Breakdown

  • Component-based: the UI is split into small, reusable, independent pieces (function components in modern React).
  • JSX: an HTML-like syntax inside JavaScript, compiled (by Babel/Vite) to React.createElement() calls.
  • Virtual DOM: a lightweight JS copy of the real DOM. On state change, React builds a new virtual tree, diffs it against the old one (reconciliation) and updates only the changed real DOM nodes.
  • Declarative: you describe what the UI should look like for a given state; React works out how to update it.
  • One-way data flow: data moves parent → child through props.
  • Hooks: useState, useEffect, useRef, useContext give function components state and lifecycle behaviour. 
// Create a project (Vite is the modern tool; create-react-app is deprecated)
// npm create vite@latest my-app -- --template react
// cd my-app && npm install && npm run dev

// src/App.jsx
import { useState, useEffect } from "react";

// Child component receiving props (read-only)
function Greeting({ name }) {
  return <h2>Hello, {name}!</h2>;          // {} embeds JS expressions in JSX

export default function App() {
  const [count, setCount] = useState(0);      // state: [value, setter]
  const [users, setUsers] = useState([]);

  // Side effect: runs after render. [] = only once on mount
  useEffect(() => {
    fetch("http://localhost:5000/api/users")   // talks to the Express backend
      .then(res => res.json())
      .then(data => setUsers(data));
  }, []);

  return (
    <div>
      <Greeting name="Asha" />
      <button onClick={() => setCount(count + 1)}>Clicked {count}</button>
      <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>
    </div>
  );
}

Real-world example: On an e-commerce page, ProductCard is one component reused 50 times with different props, while the cart count is state that updates the header instantly without a page reload.

Exam Trap:
  • React is a library, not a framework (Angular is a framework).
  • Never modify state directly (count++); always use the setter (setCount). State updates are asynchronous/batched.
  • Lists need a unique key prop. JSX uses className and htmlFor, not class/for.
  • Components must start with a capital letter; a component must return a single root (or a Fragment <></>).
  • Props are immutable inside the child.

2. Introduction to NodeJS

Core Concept

Before Node.js, JavaScript ran only inside browsers. In 2009 Ryan Dahl took Google's V8 engine out of Chrome and combined it with an event-driven I/O layer, letting JavaScript run on the server. Node.js is maintained by the OpenJS Foundation.

Why Node.js was created

Traditional servers (e.g., classic Apache/PHP) create one thread per request, which wastes memory and blocks while waiting for disk or database. Node.js handles thousands of concurrent connections on one thread using non-blocking I/O.

Feature Explanation
Asynchronous / non-blocking I/O Operations like file or DB access do not stop the main thread
Event-driven Code reacts to events (request received, file read finished)
Single-threaded event loop One main thread runs your JS; I/O is delegated
Very fast V8 compiles JS to machine code
Cross-platform Windows, Linux, macOS
Huge ecosystem NPM, the largest package registry
Full-stack JS Same language on frontend and backend; JSON everywhere

Where Node.js is used (and not used)

Good fit (I/O-heavy) Poor fit (CPU-heavy)
REST APIs, chat apps, streaming, real-time dashboards, microservices, CLI tools Video encoding, heavy image processing, large number crunching (blocks the single thread unless using Worker Threads) 
// Smallest possible Node.js web server (core http module, no Express)
const http = require("http");

const server = http.createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain" });
  res.end("Hello from Node.js");
});

server.listen(3000, () => console.log("Listening on http://localhost:3000"));
Key Concept: Node.js = V8 + libuv + core modules. It excels at I/O-bound tasks, not CPU-bound tasks.
Exam Trap: Node.js is not a language, a framework or a library. It is a runtime environment. It does not have the browser's window or document; it has global/globalThis and process.

3. What is Node.js (Definition and Architecture)

Core Concept

Node.js is an open-source, cross-platform, server-side JavaScript runtime environment built on Chrome's V8 engine, which uses an event-driven, non-blocking I/O model.

Architecture Components

  • V8 Engine (C++): parses and compiles JavaScript to machine code.
  • libuv (C): cross-platform library providing the event loop, thread pool (default size 4) and async file/network/DNS operations.
  • Node Bindings: C++ glue connecting JS to the C/C++ libraries.
  • Node Core API: built-in modules (fs, http, path, os, events, crypto, stream, url, util).

Exam Trap: "Node.js is single-threaded" is only true for your JavaScript code. Internally, libuv uses a thread pool for file system, DNS, crypto and zlib tasks. Node.js is built on V8 (Chrome's engine) but is not a browser.

4. Introduction to NPM

Core Concept

NPM (Node Package Manager) is the default package manager for Node.js. It has three parts: the online registry (npmjs.com, millions of packages), the CLI tool (npm) and the website. It installs, updates and manages project dependencies. It is installed automatically with Node.js.

5. Node Process Model

Core Concept

Traditional servers use the multi-threaded request/response model: one thread per client. Node.js uses the Single Threaded Event Loop Model: one main thread handles all requests and offloads blocking work to the system / libuv thread pool, then runs the callback when the work is done.

Step-by-step Request Handling

  1. Clients send requests; they are placed in the Event Queue.
  2. The Event Loop (single thread) picks requests one by one.
  3. If a request is simple (non-blocking), it is processed and the response returned immediately.
  4. If it needs blocking I/O (DB, file, network), it is handed to a worker thread from the Thread Pool (libuv) / OS.
  5. The event loop is free to take the next request.
  6. When the worker finishes, its callback is queued and executed by the event loop, and the response is sent. 
 Client 1 ─┐                       ┌───────────────────────┐
 Client 2 ─┼─► Event Queue ──────► │ EVENT LOOP (1 thread) │
 Client 3 ─┘                       └───┬───────────────▲───┘
                                       │ blocking I/O  │ callback
                                       ▼               │
                              ┌──────────────────────────────┐
                              │ Thread Pool (libuv, 4 default)│
                              │ fs · DNS · crypto · zlib · DB │
                              └──────────────────────────────┘

Event Loop Phases (in order)

# Phase What runs
1 Timers setTimeout, setInterval callbacks
2 Pending callbacks Deferred system I/O callbacks
3 Idle, prepare Internal use
4 Poll Retrieve new I/O events; run I/O callbacks
5 Check setImmediate callbacks
6 Close callbacks e.g. socket.on("close")

Between every phase, Node drains process.nextTick queue first, then the Promise microtask queue. 

console.log("1 sync start");
setTimeout(() => console.log("5 setTimeout"), 0);
setImmediate(() => console.log("6 setImmediate"));
Promise.resolve().then(() => console.log("4 promise microtask"));
process.nextTick(() => console.log("3 nextTick"));
console.log("2 sync end");
// Output order: 1, 2, 3 (nextTick), 4 (promise), 5/6 (timeout vs immediate*)
// *from the main module the order of 5 and 6 is not guaranteed;
//  inside an I/O callback, setImmediate always runs first.

// The process object
console.log(process.pid, process.platform, process.version);
console.log(process.argv);        // [node path, script path, ...args]
console.log(process.env.PORT);    // environment variable
process.on("exit", (code) => console.log("Exit code", code));
// process.exit(0)  → terminate; 0 = success, non-zero = error

// Blocking vs non-blocking
const fs = require("fs");
const a = fs.readFileSync("big.txt");           // BLOCKS the event loop
fs.readFile("big.txt", () => {});               // does NOT block
Multi-threaded (e.g., Java servlet) Node.js Event Loop
New thread per request One thread for all requests
High memory, context switching Low memory footprint
Good for CPU-heavy work Good for I/O-heavy work
Race conditions / locks possible No thread-sync issues in your JS code
Key Concept: Priority order: synchronous code → process.nextTick → Promise microtasks → event loop phases (timers → poll → check ...).
Exam Trap: A CPU-heavy loop or any *Sync method (e.g., readFileSync) blocks every user of the server. setImmediate runs in the check phase after poll; nextTick runs before the event loop continues (and before promises). Node.js can scale across CPU cores using the cluster module, worker_threads or PM2, because one process uses just one core.

8. Modules in NodeJS

Core Concept

A module is a self-contained file (or folder) of code with its own private scope that exposes only chosen parts to other files. In Node.js each file is a module. Modules give encapsulation, reusability, maintainability and namespacing.

Types of Modules

Type Description Load syntax
Core (built-in) Ship with Node require("fs") or require("node:fs")
Local (user-defined) Your own files require("./utils")
Third-party Installed from NPM into node_modules require("express")

Commonly Used Core Modules

Module Purpose
fs File system (read, write, delete)
path File path utilities
http / https Create servers, make requests
os Operating system information
events EventEmitter (observer pattern)
url, querystring URL parsing
crypto Hashing, encryption, random bytes
stream, zlib Streaming data, compression
util Helpers such as promisify

CommonJS vs ES Modules

Aspect CommonJS (CJS) ES Modules (ESM)
Import const x = require("x") import x from "x"
Export module.exports = ... export / export default
Loading Synchronous, at runtime Asynchronous, statically analyzed
Enable Default in Node (.js, .cjs) "type": "module" in package.json or .mjs
__dirname, __filename Available Not available (use import.meta.url)
Top-level await No Yes
File extension in path Optional Required (./math.js)

How require() resolves a module

 require("x")
   1. Is "x" a core module (fs, http...)?            → load it
   2. Starts with ./ ../ or /  ?                      → load that file/folder
        tries: x, x.js, x.json, x.node, x/package.json "main", x/index.js
   3. Otherwise look in ./node_modules/x, then ../node_modules/x,
      then ../../node_modules/x ... up to the root
   4. Not found → Error: Cannot find module 'x'
   Result is CACHED in require.cache (file runs only ONCE)
Key Concept: Modules are cached after the first require. Every later require of the same file returns the same object, which makes modules natural singletons (e.g., a shared DB connection).
Exam Trap: Variables declared in a module are not global; they are private to the file. Use require("./file") with ./ for local files; without it Node searches core modules and node_modules. You cannot mix require and import freely: require is not defined in ES module scope and Cannot use import statement outside a module are classic errors. Core modules do not need installation. Circular dependencies return a partially filled exports object.

9. Understanding exports and require

Core Concept

  • require(path): a function that loads a module and returns its module.exports value.
  • module.exports: the object that is actually returned to the caller. It starts as an empty object {}.
  • exports: just a shorthand reference that initially points to the same object as module.exports. 
 At the start of every module Node does:   exports = module.exports = {}

   exports ─────────┐
                    ├──► { }   ◄── this object is what require() returns
   module.exports ──┘

 exports.a = 1            → adds property to the shared object          ✔ works
 exports = function(){}   → rebinds ONLY the local variable "exports"   ✘ lost
 module.exports = fn      → replaces the object that require() returns  ✔ works

Pattern 1: Attach properties (named exports)

// math.js
exports.add = (a, b) => a + b;
exports.sub = (a, b) => a - b;
const PI = 3.14159;          // private, not exported

// app.js
const math = require("./math");
console.log(math.add(2, 3));          // 5
const { sub } = require("./math");    // destructuring the result
console.log(sub(5, 1));               // 4
console.log(math.PI);                 // undefined (private)

Pattern 2: Replace module.exports (single export)

// greet.js
module.exports = function (name) { return `Hello ${name}`; };

// user.js
class User { constructor(n) { this.name = n; } }
module.exports = User;

// app.js
const greet = require("./greet");
const User  = require("./user");
console.log(greet("Asha"), new User("Ravi").name);

Pattern 3: Export an object of many things

// utils.js
const square = x => x * x;
const cube = x => x * x * x;
module.exports = { square, cube };       // shorthand properties

// app.js
const { square, cube } = require("./utils");

The classic mistake

// bad.js
exports = { hello: () => "hi" };          // ✘ only rebinds local variable
// main.js
console.log(require("./bad"));            // {}  ← EMPTY OBJECT

// fixed: module.exports = { hello: () => "hi" };

// Mixing: after this the exports.x line is IGNORED
exports.x = 1;
module.exports = { y: 2 };               // require() returns { y: 2 } only

Caching demonstration

// counter.js
let count = 0;
module.exports = { inc: () => ++count };
console.log("counter.js loaded");        // prints only ONCE

// app.js
const a = require("./counter");
const b = require("./counter");          // served from cache
a.inc(); b.inc();
console.log(a === b);                    // true (same object)
console.log(a.inc());                    // 3

Equivalent ES Module syntax

// math.mjs  (or "type":"module")
export const add = (a, b) => a + b;          // named export
export default function sub(a, b) { return a - b; }   // one default export

// app.mjs
import sub, { add } from "./math.mjs";           // default + named
import * as math from "./math.mjs";              // namespace import
const mod = await import("./math.mjs");          // dynamic import
Feature exports.x = ... module.exports = ...
Can export a function / class directly No Yes
Can export many named things Yes Yes (as an object)
Safe to reassign No (breaks the link) Yes
What require returns Always module.exports Always module.exports
Exam Trap (very high-yield):
  • require() always returns module.exports, never exports.
  • exports = something does not work; module.exports = something does.
  • If you assign module.exports after exports.x, the earlier exports.x is lost.
  • require is synchronous and cached, so the module code executes only once.
  • Destructuring const { add } = require("./math") works only for object-style exports.
  • In ESM there can be only one default export per file but many named exports.

10. Creating Modules

Core Concept

Creating a module means putting related functionality in its own file, deciding what to expose, and loading it where needed. Follow the Single Responsibility Principle: one module, one purpose.

Step-by-Step

  1. Create a new file (e.g., calculator.js).
  2. Write functions/classes/constants; keep helpers private.
  3. Export the public API via module.exports (or export).
  4. Import it with require("./calculator") in another file.
  5. Run the main file with node app.js.

Example Project Structure

 project/
 ├── app.js                  ← entry point
 ├── package.json
 ├── modules/
 │    ├── calculator.js      ← functions module
 │    ├── logger.js          ← class module
 │    └── config.js          ← constants module
 └── utils/
      ├── index.js           ← "barrel": re-exports everything in the folder
      ├── string.js
      └── date.js

Module 1: Functions (calculator.js)

// modules/calculator.js
function add(a, b) { return a + b; }
function divide(a, b) {
  if (b === 0) throw new Error("Cannot divide by zero");
  return a / b;
}
function _validate(n) { return typeof n === "number"; }   // private helper (not exported)

module.exports = { add, divide };

Module 2: Class (logger.js)

// modules/logger.js
const EventEmitter = require("events");

class Logger extends EventEmitter {
  constructor(prefix = "APP") { super(); this.prefix = prefix; }
  log(msg) {
    const line = `[${this.prefix}] ${new Date().toISOString()} ${msg}`;
    console.log(line);
    this.emit("logged", line);          // custom event
  }
}
module.exports = Logger;                // export the class itself

Module 3: Constants / Configuration (config.js)

// modules/config.js
module.exports = Object.freeze({
  PORT: process.env.PORT || 5000,
  DB_URL: process.env.DB_URL || "mongodb://localhost:27017/mydb",
  APP_NAME: "MERN Backend"
});

Module 4: Factory / Singleton pattern

// modules/db.js
let connection = null;                  // private state, lives in module scope
module.exports = {
  connect() {
    if (!connection) { connection = { connectedAt: Date.now() }; console.log("DB connected"); }
    return connection;                  // same connection every time (cached module)
  }

Barrel index.js Clean folder-level imports
Exam Trap: Forgetting ./ in require("calculator") makes Node look in node_modules and throw Cannot find module. If you forget to export a function, it is undefined or "is not a function" in the importer. Because of caching, module-level variables are shared across all importers. Circular requires (A requires B, B requires A) give incomplete exports; restructure to avoid them. In ESM, the file extension in the import path is mandatory.
